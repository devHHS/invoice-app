**한 일**

**막혔던 것과 원인**
- `InvoiceService` 생성자에 `VendorRepository`를 추가할 때, 기존 생성자를 고치는 대신 **별도의 두 번째 생성자**(`InvoiceService(VendorRepository)`)를 만들어 `variable ... might not have been initialized` 에러 — "생성자는 실행 시점에 하나만 선택되어 호출된다"는 실행 모델을 아직 직관적으로 못 잡고 있음, 파라미터 두 개짜리 생성자 하나로 합치라는 설명 후 해결 (`learning-records/0013`)
- `toEntity()`에서 `vendorRepository.findById(...)`를 두 번 호출(한 번은 존재 확인만 하고 버림, 한 번은 `.get()`으로 다시 조회) — 첫 호출의 반환값을 변수로 받아 재사용하라고 짚어주자 바로 수정
- IntelliJ가 `@JoinColumn`에 "Cannot resolve column 'vendor_id'" 경고 — 실제 DB엔 컬럼이 이미 있었음(psql로 확인), 원인은 IntelliJ Database 툴 창의 스키마 캐시가 앱 재시작과 별개로 갱신 안 된 것 — 데이터소스 Refresh로 해결 (`docs/CURRICULUM.md` "자주 막히는 곳"에 기록)
- 테스트 중 JSON body의 `vendorId` 줄을 지우다 트레일링 콤마를 남겨 400(JSON parse error) — 실제 파일 내용을 다시 확인해 정상 상태임을 스스로 재확인 후 재실행하여 해결

**다음에 이어질 것**
- `Invoice.storeName` 필드 완전 제거 + `InvoiceRepository`의 검색 쿼리 메서드를 `findAllByVendor_StoreNameContaining`처럼 연관관계 기준으로 전환 — 새 레슨(0021) 예정
- 커밋 메시지 추천: `feat: wire Invoice-Vendor lookup in service and DTOs`

- `VendorService.findById()`에서 `orElseThrow` 대신 `orElse(() -> new VendorNotFoundException(id))`를 써서 `Target type of a lambda conversion must be an interface` 컴파일 에러 — `orElse(Vendor)`는 파라미터가 구체 클래스라 람다(함수형 인터페이스 전용)를 못 받는다는 원리 설명 후 스스로 `orElseThrow`로 수정
- `VendorController`의 `findById`/`update`/`delete`에 `@PathVariable Long id`는 있는데 매핑 경로에 `/{id}`가 빠져 있어 `findAll()`과 `findById()`가 둘 다 `GET /vendors`로 겹치는 `Ambiguous mapping` 기동 에러 발생 — 처음엔 `findById`만 고치고 `update`/`delete`는 같은 문제를 못 알아채서 재확인 요청, 두 번째 검토에서 전부 수정 확인
- 검증 curl에서 `issuedAt`을 `"2026-09-05"`(날짜만)로 보내 `LocalDateTime` 역직렬화 실패로 400이 남 — `Vendor` 로직과 무관하게 `@RequestBody` 파싱이 Controller 진입 전에 실패한 것이라는 점, 그리고 에러를 읽을 때 스택트레이스의 `at ...` 줄보다 최상단 `message` + 예외 타입 이름 + `reference chain`(어느 필드인지)을 먼저 보는 습관을 설명 — 시간까지 포함한 형식으로 재요청해 404 확인
- 시간 압박(30~60분) 속에서도 다크 모드 스타일 변경 요청이 중간에 들어와 잠깐 옆길로 샜지만 본 작업(Vendor 3계층)으로 바로 복귀함
