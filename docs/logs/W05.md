## Phase 5 — 백엔드 컨테이너화 (레슨 0016)

**한 일**
- `Dockerfile` 멀티스테이지 빌드 작성: 빌드 스테이지(`maven:3.9-eclipse-temurin-21`)에서 jar 생성 → 실행 스테이지(`eclipse-temurin:21-jre`)로 jar만 복사
- IntelliJ가 자동 생성한 기본 `Dockerfile`(ubuntu 베이스 + `top -b` 플레이스홀더)이 프로젝트와 무관한 범용 스캐폴드라는 것 확인 후 전부 교체
- `docker-compose.yml`에 `app` 서비스 추가 — `build: .`, `depends_on: db`, `ports: 8080:8080`, `SPRING_DATASOURCE_URL` 환경변수로 DB 주소를 `db:5432`로 덮어씀(로컬 실행용 `application.yml`은 그대로 두고 컨테이너 실행 시에만 값을 바꾸는 방식)
- `docker compose up --build`로 DB+앱 함께 기동 성공, 로그에서 실제 `jdbc:postgresql://db:5432/invoice-db` 접속 확인, `GET /invoices` 정상 응답 확인
- `docs/CURRICULUM.md` Phase 5의 Dockerfile 항목 + Month 1 완료 조건("`docker compose up` 하나로 API가 뜬다") 체크 완료

**질문/맥락 확장**
- "왜 이걸 하는지 모르겠다"는 질문에서 시작해 엔터프라이즈 컨테이너화 이유, 멀티스테이지 Dockerfile vs Cloud Native Buildpacks vs 레이어드 jar 비교까지 조사 후 설명 — 레이어드 jar 최적화는 오늘 스코프(새 개념 2개로 이미 충분)에서 제외하고 `NOTES.md` 백로그로 저장(합의)
- 사내에서 본 "Artifactory에서 jar 받아 AWS로 배포"가 오늘 배운 것과 같은지 질문 — Artifactory가 jar 저장소이자 Docker 레지스트리 역할도 겸한다는 점, 사내 파이프라인이 전통 방식(jar + EC2)인지 컨테이너 방식(이미지 + ECS)인지 구분하는 기준(CI 로그에 `docker build`/`push`가 있는지)을 안내

**막혔던 것과 원인**
- 특별히 막힌 지점 없음 — 빌드 스테이지/실행 스테이지/compose 값 전부 힌트(빈칸 + 설명 주석)만으로 스스로 정확히 채움

**작업 방식 관련 확인**
- 이미 완성한 코드(Dockerfile)에는 "설명 주석"(문서화 목적)을, 아직 안 쓴 부분(compose)에는 "빈칸 + 설명 주석"(직접 채우게)을 선호한다는 것 확인 — `NOTES.md`에 기록, 다음 레슨부터 기본 스캐폴딩 방식으로 채택
