# W04 세션 요약

## Phase 4 마무리 — Validation 에러 응답 통일 (레슨 0014)

**한 일**
- `ErrorResponse` DTO(`message`, `status`) 작성 — 처음엔 getter 누락(직렬화 시 `{}`로 나가는 문제), 힌트 한 번으로 스스로 추가
- 기존 404 핸들러(`InvoiceNotFoundException`)를 `ResponseEntity<String>`에서 `ResponseEntity<ErrorResponse>`로 리팩터링
- `MethodArgumentNotValidException`을 잡는 400 핸들러 신규 작성 — Spring이 직접 던지는 예외라는 점(우리가 던지는 것과 대조)을 레슨 0013의 "던지기 vs 가로채기" 연장으로 이해
- `getFieldError()`가 `null`일 수 있는 경우(클래스 레벨 검증 실패 시)를 예측 질문으로 짚고, 삼항 연산자(`? :`)로 방어 코드 작성 — 이번 세션에서 처음 쓴 문법, 한 번 설명 후 바로 정확히 적용
- `requests.http`로 404/400 응답이 동일한 `{"message": ..., "status": ...}` 구조로 나오는 것 확인
- `docs/CURRICULUM.md` Phase 4 전 항목 체크 완료

**막혔던 것과 원인**
- `ErrorResponse` 생성자 두 번째 인자에 `HttpStatus.BAD_REQUEST`(enum)를 그대로 넣어 컴파일 에러 — `ResponseEntity.status(HttpStatus...)`와 `ErrorResponse`의 `int status` 필드, 이름이 같은 "상태"가 두 군데서 다른 타입으로 쓰여 혼동. 에러 메시지(`incompatible types`)를 같이 읽고 두 용법을 대조해서 정리 후 해결
- 404 핸들러에서 `ErrorResponse` 두 번째 인자에 `400`을 잘못 넣은 복붙 실수 — "실제 상태 코드와 JSON 본문 필드가 일치해야 한다"는 질문으로 스스로 발견

## Phase 5 — 검색 기능 (레슨 0015)

**한 일**
- API-first 순서(Controller → Service → Repository)로 `GET /invoices?storeName=...` 검색 기능 구현
- `InvoiceRepository`에 `findAllByStoreNameContaining(String storeName)` 쿼리 메서드 선언 — 본문 없이 이름만으로 SQL 자동 생성
- `application.yml`에 `spring.jpa.show-sql: true` 추가, 콘솔에서 실제 생성된 SQL(`where store_name like ?`) 직접 확인
- 동적 프록시가 쿼리 메서드를 처리하는 4단계(이름 파싱 → 리플렉션으로 필드 검증 → SQL 조각 생성 → 프록시 메서드 몸통에 대입)를 구체적으로 재설명 — "말로는 알겠는데 정확히는 이해 못 했다"고 스스로 밝혀 기존보다 더 깊게 짚음
- `docs/CURRICULUM.md` Phase 5 — 검색 기능 항목 체크 완료

**막혔던 것과 원인**
- `@RequestParam(required = false)`의 의도(파라미터 없어도 정상 동작)와 반대로, `storeName == null`일 때 예외를 던지도록 처음 작성 — 코드만 보고 예측해보라는 질문으로 스스로 수정
- Repository 쿼리 메서드의 리턴 타입을 `List<InvoiceResponse>`(DTO)로 선언 — "Repository는 Entity와만 대화한다"는 원칙(레슨 0008 레퍼런스)을 이번엔 바로 못 떠올림. 컴파일 에러와 함께 계층 책임을 다시 질문해 스스로 `List<Invoice>`로 정정
