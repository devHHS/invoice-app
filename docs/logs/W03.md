## 화요일 — Controller가 DTO 반환하도록 변경 (레슨 0009)

**한 일**
- `InvoiceController`의 `save`, `findAll`, `findById`, `update` 네 메서드 전부 `Invoice` 대신 `InvoiceRequest`/`InvoiceResponse`를 주고받도록 변경. 변환 로직은 계획대로 각 메서드 본문에 임시로 둠 (`deleteById`는 DTO와 무관해 그대로 둠)
- `findAll`은 `Invoice` 리스트를 `InvoiceResponse` 리스트로 바꾸는 데 `.stream().map(...).toList()` 처음 사용 — 람다 문법을 이번에 처음 접함
- IntelliJ가 `findById` 작성 중 `Extract Method` 리팩터링을 제안(중복 코드 감지) — 오늘은 적용하지 않고 넘어감, 내일(변환 로직을 Service로 이동) 계획과 자연스럽게 연결됨
- `requests.http`로 POST/GET/PUT 직접 확인 — 응답 JSON이 `InvoiceResponse` 모양으로 정상 반환됨
- 이해 체크 3문제 구두 답변, 전부 정확

**막혔던 것과 원인**
- 변수명 오타(`invoiceRespoens` vs `invoiceRequest`) — "cannot resolve symbol" 에러로 스스로 발견 후 수정
- `findById` 작성 중 `save()` 코드를 그대로 복붙해 파라미터 타입(`@PathVariable InvoiceRequest`)과 메서드 본문(저장 로직)이 목적과 안 맞았음 — 원래 메서드의 목적(조회 vs 저장)을 먼저 확인하는 습관이 아직 약함
- `findAll`에서 `.stream().map(...).toList()` 체인의 결과를 저장/리턴하지 않고 `return findAll();`(자기 자신 재귀 호출)을 씀 — 무한 재귀로 `StackOverflowError` 위험이 있었음. 스트림 체인은 `return`을 체인 맨 앞에 한 번만 붙이면 된다는 점을 명확히 하지 않은 채 시작한 게 원인
- PUT 테스트 시 존재하지 않는 `id=1`로 요청해 `ObjectOptimisticLockingFailureException` 발생 — 코드 버그가 아니라 테스트 데이터 상태 착각. GET으로 실제 존재하는 id를 먼저 확인하는 습관 필요

**다음(수요일 — 변환 로직을 Service로 이동)에 이어질 것**
- 오늘 Controller 메서드마다 반복된 변환 코드(요청/응답)를 `InvoiceService`로 옮겨서 Controller를 얇게 만들기
- IntelliJ가 오늘 제안했던 "Duplicated code" 경고가 이 작업의 동기로 자연스럽게 연결됨
