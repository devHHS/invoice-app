## 화요일 — Controller가 DTO 반환하도록 변경 (레슨 0009)

**한 일**
- `InvoiceController`의 `save`, `findAll`, `findById`, `update` 네 메서드 전부 `Invoice` 대신 `InvoiceRequest`/`InvoiceResponse`를 주고받도록 변경. 변환 로직은 계획대로 각 메서드 본문에 임시로 둠 (`deleteById`는 DTO와 무관해 그대로 둠)
- `findAll`은 `Invoice` 리스트를 `InvoiceResponse` 리스트로 바꾸는 데 `.stream().map(...).toList()` 처음 사용 — 람다 문법을 이번에 처음 접함
- IntelliJ가 `findById` 작성 중 `Extract Method` 리팩터링을 제안(중복 코드 감지) — 오늘은 적용하지 않고 넘어감, 내일(변환 로직을 Service로 이동) 계획과 자연스럽게 연결됨
- `requests.http`로 POST/GET/PUT 직접 확인 — 응답 JSON이 `InvoiceResponse` 모양으로 정상 반환됨
- 이해 체크 3문제 구두 답변, 전부 정확

**막혔던 것과 원인**
- 변수명 오타(`invoiceRespoens` vs `invoiceRequest`) — "cannot resolve symbol" 에러로 스스로 발견 후 수정
- `findById` 작성 중 `save()` 코드를 그대로 복붙해 파라미터 타입(`@PathVariable InvoiceRequest`)과 메서드 본문(저장 로직)이 목적과 안 맞았음 — 원래 메서드의 목적(조회 vs 저장)을 먼저 확인하는 습관이 아직 약함
- `findAll`에서 `.stream().map(...).toList()` 체인의 결과를 저장/리턴하지 않고 `return findAll();`(자기 자신 재귀 호출)을 씀 — 무한 재귀로 `StackOverflowError` 위험이 있었음. 스트림 체인은 `return`을 체인 맨 앞에 한 번만 붙이면 된다는 점을 명확히 하지 않은 채 시작한 게 원인
- PUT 테스트 시 존재하지 않는 `id=1`로 요청해 `ObjectOptimisticLockingFailureException` 발생 — 코드 버그가 아니라 테스트 데이터 상태 착각. GET으로 실제 존재하는 id를 먼저 확인하는 습관 필요

**다음(수요일 — 변환 로직을 Service로 이동)에 이어질 것**
- 오늘 Controller 메서드마다 반복된 변환 코드(요청/응답)를 `InvoiceService`로 옮겨서 Controller를 얇게 만들기
- IntelliJ가 오늘 제안했던 "Duplicated code" 경고가 이 작업의 동기로 자연스럽게 연결됨

## 수요일 — 변환 로직을 Service로 이동 (레슨 0010)

**한 일**
- `save`부터 시작해 `findById`, `findAll`, `update` 순서로 전부 `InvoiceService`가 `InvoiceRequest`/`InvoiceResponse`를 직접 주고받도록 변경. `InvoiceController`의 각 메서드는 변환 없이 `return invoiceService.xxx(...);` 한 줄로 줄어듦
- 도중에 "Controller나 Service 중 뭘 먼저 고치는 게 실무에서 자연스러운가" 질문 → Service 먼저(계약을 정하고 컴파일 에러를 따라가는 방식)와 Controller 먼저(API-first/outside-in, 원하는 결과부터 정하고 거슬러 올라가는 방식) 둘 다 실무에서 쓰인다고 정리. 본인이 "프론트엔드 먼저 구현 후 백엔드"에 비유하며 API-first 쪽을 선호한다고 밝혀, `findById`/`findAll`/`update` 전부 이 순서(Controller 먼저 → 컴파일 에러 보고 Service 수정)로 진행
- 4개 메서드에 반복되던 변환 코드를 `private toEntity(InvoiceRequest)` / `private toResponse(Invoice)` 헬퍼 메서드로 추출 — 어제 IntelliJ가 지적했던 중복(Extract Method 제안)을 실제로 해소. `findAll`의 스트림 매핑도 `.map(this::toResponse)`(메서드 참조)로 정리
- "중간 변수를 자주 쓰는 게 거슬린다"는 스스로의 관찰 → `save`/`findById`/`update`를 중간 변수 없이 바로 `return`하는 형태로 추가 정리
- `requests.http`로 POST/GET(단건·전체)/PUT 전부 재확인 — 응답 정상, PUT은 새 행이 아니라 기존 `id`가 수정됨을 직접 확인
- 레퍼런스 0009(`save()` 전/후 흐름)를 처음엔 커스텀 CSS 시퀀스 다이어그램으로 작성했다가, 사용자가 "정통 UML 형태로 그려달라"고 요청 → Mermaid(CDN)로 재작성. 기존 레퍼런스(0002, 0003, 0008)도 전부 Mermaid로 소급 변환, 안 쓰게 된 `assets/sequence-diagram.css` 삭제

**막혔던 것과 원인**
- `save`를 처음 고칠 때 `InvoiceService.save`의 파라미터/리턴 타입만 바꾸고 본문의 `invoiceRepository.save(invoice)`를 실수로 `save(invoice)`(자기 자신 재귀 호출)로 잘못 옮김 — `invoiceRepository.`가 통째로 빠진 것. 본인이 스스로 "전체 되돌리기" 요청해 처음부터 다시 진행
- `update`를 헬퍼로 옮기는 과정에서 `toResponse`가 파라미터 `invoice` 대신 자기 자신(`invoiceResponse`)의 getter를 참조하는 버그 발생(`invoiceResponse.setId(invoiceResponse.getId())`) — 컴파일은 되지만 항상 `null`을 반환하는, 컴파일러가 못 잡는 논리 버그. 필드 5개 중 처음엔 1개만 고쳐서 재확인 필요했음
- `update`에서 `invoice.setId(id)`를 `invoiceRepository.save(invoice)` **이후**에 호출해 id가 안 채워진 채 저장되는 순서 버그 재발(W02에서 다룬 것과 같은 유형) — 원래 코드의 순서를 먼저 확인하는 습관으로 스스로 정정
- Claude(나)가 "save 관련만 고쳐달라"는 범위를 벗어나 `findAll`/`findById`/`update`/Controller 전체를 임의로 리팩터링한 사고 발생 — 사용자가 직접 git으로 전체 되돌리기 후 처음부터 재진행. 이후 명시적으로 요청한 범위만 수정하도록 재조정
- Claude가 레퍼런스 0009 작성 시 실제 코드(인라인 변환)를 재확인하지 않고 이전에 되돌려진 버전(`toEntity`/`toResponse` 사용)을 그대로 문서화 — 사용자가 지적해 실제 코드에 맞게 재작성

## 금요일 — 입력 검증 (레슨 0011)

**한 일**
- 목요일 Python 트랙은 매주 반복되는 고정 패턴이라 이번부터 세션 시작 시 확인 없이 자동으로 스킵하기로 함
- `pom.xml`에 `spring-boot-starter-validation` 의존성 추가
- `InvoiceRequest`의 4개 필드 전부에 Bean Validation 애노테이션 적용: `storeName`/`category`(`@NotBlank`), `amount`(`@NotNull` + `@Positive`), `issuedAt`(`@NotNull`) — 문자열엔 `@NotBlank`, 그 외 타입(`LocalDateTime`)엔 `@NotNull`만 가능하다는 원리를 스스로 `category`에 적용해 확인
- `InvoiceController`의 `save`(POST)뿐 아니라 `update`(PUT)의 `@RequestBody`에도 `@Valid`를 붙임 — 계획엔 POST만 있었지만, "검증은 HTTP 메서드가 아니라 `@Valid`가 붙어 있는지로만 결정된다"는 걸 스스로 짚어 PUT까지 확장
- `requests.http`로 음수 금액, 빈 `storeName`/`category`, `null`/형식이 잘못된 `issuedAt` 등 각 케이스별 400 응답과 메시지를 직접 확인
- 에러 메시지 영문 문구(`"Amount have to be..."` → `"Amount must be positive"`)를 네이티브 표현으로 다듬음
- "JSON 파싱 실패(Jackson)"와 "Bean Validation 실패"가 서로 다른 단계라는 걸 실제 에러로 확인 — 형식이 잘못된 `issuedAt`("2:00:00")을 보내면 `@NotNull`이 아니라 `HttpMessageNotReadableException`으로 먼저 막힘. JSON→객체 변환이 성공해야 그다음 `@Valid` 검증이 실행된다는 순서를 이해

**막혔던 것과 원인**
- `@Valid`를 처음엔 `findById`의 `@PathVariable Long id`에 잘못 붙임 — 검증이 필요한 대상(요청 본문 DTO)이 아니라 상관없는 파라미터에 붙여 아무 효과가 없었음. 애초에 검증 애노테이션이 있는 DTO가 아니라는 점을 짚어 `save`의 `@RequestBody`로 정정
- `issuedAt`(비-문자열 타입)에 `@NotBlank`를 쓰려다 질문으로 먼저 확인 — `@NotBlank`는 `CharSequence` 전용이라 `LocalDateTime`엔 타입 자체가 안 맞는다는 걸 코드로 시도하기 전에 짚고 넘어감
