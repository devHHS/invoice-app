**한 일**
- `docker-compose.yml` 작성 (`postgres:15`, `POSTGRES_DB`/`USER`/`PASSWORD`, `ports: 5432:5432`) 후 프로젝트 루트로 위치 이동 (`src/main/docker` → 루트가 Docker/Spring Boot 양쪽 다 더 표준적인 위치라고 확인)
- `pom.xml`에 `spring-boot-starter-data-jpa` 추가 — DB 연결을 실제로 검증하려면 필요했음 (JPA starter 없이는 `application.yml`의 `datasource` 설정이 아무 효과 없음)
- `application.properties` → `application.yml`로 전환, `spring.datasource`/`spring.jpa.hibernate.ddl-auto` 설정
- 최종적으로 `HikariPool-1 - Start completed`, `Started InvoiceAppApplication` 확인 — DB 연결 성공

**막혔던 것과 원인**
- `docker-compose.yml`의 `POSTGRES_DB = invoice` 처럼 `=` 양옆에 공백을 넣어 값이 제대로 안 먹힌 적 있음 → docker compose의 `KEY=VALUE` 문법은 공백 허용 안 함
- YAML 들여쓰기·오타(`passowrd`, `passoword`) 두 번 반복 — YAML은 오타 나도 에러 없이 조용히 무시되는 키가 될 수 있어서 발견이 늦어짐
- `POSTGRES_DB` 값을 나중에 바꿨는데 연결 시 `database "invoice-db" does not exist` — postgres 컨테이너는 **최초 생성 시 한 번만** 환경변수로 DB를 만들기 때문에, 이후 값을 바꾸면 `docker compose down -v`로 볼륨째 재생성해야 반영됨
- IntelliJ의 "Port 8080 was already in use" — DevTools의 `restartedMain` 때문에 정지 버튼이 이전 프로세스를 완전히 못 죽인 경우 있었음 (`lsof` + `kill`로 해결)

**다음(토요일 — Invoice Entity)에 이어질 것**
- `spring-boot-starter-data-jpa`는 이미 추가되어 있으니 바로 `@Entity` 클래스 작성으로 넘어갈 수 있음
- `ddl-auto: update` 설정도 이미 되어 있어 Entity를 만들면 테이블이 자동 생성되는 걸 바로 확인 가능

## 토요일 — Invoice Entity 작성, id 생성 전략 실습

**한 일**
- `Invoice.java` 작성: `@Entity`, `@Id`, `@GeneratedValue`, no-args 생성자, getter/setter, 필드 5개(`id`, `storeName`, `amount`, `issuedAt`, `category`)
- 앱 실행 후 psql·DBeaver로 `invoice` 테이블 자동 생성 직접 확인
- `@GeneratedValue(AUTO)` vs `IDENTITY` 차이를 코드 수정 → `drop table` → 재시작 → psql로 시퀀스/컬럼 정의 비교하는 실습으로 검증 (`AUTO`는 `invoice_seq`로 50씩 건너뛰며 값 할당, `IDENTITY`는 컬럼 자체가 `generated by default as identity`로 촘촘하게 채움)
- Baeldung `Student` 예시와 우리 `Invoice` 코드 차이 정리 (`@Column`/`@Transient`/`@Temporal` 생략 이유) — `reference/0006`
- JPA/Hibernate 개념 심화: 영속성 컨텍스트, no-args 생성자가 필요한 이유(리플렉션), 객체·생성자·인터페이스·매핑·Bean 용어 정리 — `reference/0001` 용어집 보강

**막혔던 것과 원인**
- DBeaver `Database` 필드에 실제 DB 이름(`invoice-db`)이 아닌 다른 값(`postgres`, `invoice-app`)을 넣어 연결 실패 → DB 클라이언트의 Database 값은 `application.yml`의 DB 이름과 정확히 일치해야 함
- `ddl-auto: update`는 새 테이블/컬럼 추가는 되지만, 기존 컬럼의 생성 전략 변경(AUTO→IDENTITY)은 반영 못 함 → `drop table` 후 재시작으로 우회. 실무에서는 이 문제를 Flyway/Liquibase 같은 마이그레이션 툴로 해결한다는 것도 개념만 짚고 넘어감 (실습은 해당 주차로 보류, `NOTES.md`에 메모)

**옆길로 샌 질문**
- "id를 UUID로 바꾸고 싶다"(URL 노출 우려) — Controller가 아직 없어 실제로 발생하지 않은 문제이고 `docs/W02.md`가 이미 `Long` 기준으로 짜여 있어 보류. W02 Controller 만들 때 다시 연결하기로 함 (`NOTES.md`에 메모)

**다음(W02)에 이어질 것**
- `InvoiceRepository extends JpaRepository<Invoice, Long>`부터 바로 시작 가능
- 생성자 주입 개념은 오늘 대화로 이미 이해 완료 — `InvoiceService`/`InvoiceController` 만들 때 바로 적용
- id 노출(UUID) 논의, Flyway/Liquibase 논의 재개 예정
