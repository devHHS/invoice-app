## Month 3 Phase 1 계속 — update 완료, delete는 내일 (2026-09-16)

**한 일**
- `update_존재하지_않으면_VendorNotFoundException을_던진다()` 작성 — 처음엔 `vendorService.update()`를 인자 없이 호출해 컴파일 에러(`required: Long,Vendor / found: no arguments`), 에러 메시지 보고 스스로 인자 채움. `existsById(null)`로 stub한 것도 스스로 짚어 `999L`로 정정

- 본인이 직접 요청해서 `update_존재하지_않으면...` 테스트를 리뷰 — `existsById`가 `false`를 리턴해 예외가 즉시 던져지므로 이후 `vendor.setId(1L)`/`setStoreName(...)` 세팅이 전혀 안 쓰인다는 걸 설명 후 정리
- `update_존재하면_수정된_Vendor를_반환한다()` — 힌트 구조 없이 처음부터 작성하다 컴파일 에러 2개(`existsById` 대신 `findById`를 stub하려다 타입 불일치, `Act`에서 `update()` 대신 `save(vendor.setStoreName())`처럼 잘못된 메서드 호출) 발생. 고친 뒤에는 `NullPointerException`(result가 null) — `vendorRepository.save(vendor)`를 stub 안 해서 발생. "mock은 stub 안 한 메서드는 기본값(null)을 리턴한다"는 설명을 처음엔 이해 못 했다가("이해를 못 했어") 단계별 재설명 후 본인 언어로 정확히 재진술함. 상세는 `learning-records/0017`

**막혔던 것과 원인**
- 힌트/구조 없이 완전히 새로 작성하는 첫 테스트(`update` 정상 케이스)에서 실수 빈도가 눈에 띄게 늘어남 — `existsById`/`findById`/`save`처럼 이름이 비슷한 Repository 메서드를 혼동, Service의 실행 경로에 있는 **모든** mock 호출을 stub해야 한다는 원칙이 아직 자동화되지 않음. 상세는 `learning-records/0017`
